# Medição de recursos

O arquivo `macos-arm64-2026-10-28.json` contém os dados brutos da comparação no Mac Apple M3 de 8 GiB. O baseline é o commit `fc30402`; a versão posterior é a branch desta auditoria. Além da medição anterior à implementação, repetimos a carga na versão original logo após medir a versão final. A outra instância do DK e os demais aplicativos do computador permaneceram ativos. A carga usou uma instância isolada, `/bin/sh`, perfis e arquivos temporários, 1/4/8 terminais e 12 mil linhas de saída por terminal. Não houve limpeza do sistema nem coleta manual de lixo.

Cada cenário registra três amostras e a mediana do RSS e da CPU por `ps`, os tipos de processo Electron, os processos filhos e o heap JavaScript do renderer pelo protocolo de diagnóstico. RSS é uma soma e pode contar páginas compartilhadas mais de uma vez. No macOS a compressão e a atividade de outros aplicativos podem modificar significativamente o RSS entre amostras; não se deve atribuir toda diferença à mudança de código. A consulta de disponibilidade no fim da execução não é uma medida de pressão.

Os testes de cancelamento do Codex usam um servidor local **simulado**, sem inferência ou comunicação com provedores; não medem a CLI real. Um teste adicional cobre o próprio shell ignorando os sinais de encerramento, além dos filhos resistentes. A medição foi realizada apenas em macOS arm64; Windows e Linux, o consumo do Codex real e a ausência de crescimento por tempo indefinido requerem validação adicional. Os 12 ciclos medidos são evidência limitada, não prova para uso ilimitado.

Reprodução: no código a medir, execute `npm run build` e `DK_BENCH_LABEL=nome npm run benchmark:resources`. O JSON é salvo em `artifacts/resource-benchmark.json` ou no caminho de `DK_BENCH_OUTPUT`. Para comparar com um checkout antigo que ainda não tenha o roteiro, copie `tests/resource-benchmark.cjs` para esse checkout. `tests/resource-idle-compare.cjs` permite três pares alternados com `DK_BASELINE_APP=/caminho/da/versao/anterior` após compilar as duas versões. O roteiro usa macOS/Linux, Node, Python 3 e `ps`, e não oferece suporte de benchmark ao Windows.

Na comparação de repouso com três pares alternados, a mediana do heap JavaScript inicial foi de 3,47 para 2,76 MiB (−20,4%); a mediana do RSS foi de 416,5 para 449,1 MiB (+7,8%), sem redução estável de RSS. A mediana de CPU foi 0,1% em ambos. Na repetição próxima da versão final, oito terminais após saída intensa passaram de 827,1 para 826,5 MiB de RSS (−0,1%), portanto não há evidência de ganho de RSS para essa carga. Ao fechar todas as sessões, o RSS amostrado foi de 822,0 para 696,3 MiB (−15,3%), mas depois do repouso foi de 699,9 para 716,9 MiB (+2,4%), o que impede atribuir um ganho duradouro a essa diferença. O encerramento explícito eliminou os filhos resistentes nos testes sintéticos (um remanescente antes e nenhum depois). Na última sequência de 12 ciclos, o RSS foi de 568,3 MiB após quatro ciclos para 599,2 MiB após 12, enquanto o heap JavaScript foi de 5,75 para 7,05 MiB; é necessária uma observação mais longa para investigar o crescimento. Valores variam com o estado do sistema; os dados completos e os cenários individuais estão no JSON.
